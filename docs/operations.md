# Эксплуатация

## Перед открытием сайта

1. Заполнить контакты, реквизиты, условия обработки данных и подтвердить публикуемые сведения.
2. Заменить иллюстративные фото на фотографии с правом использования. Добавить помещения через админку.
3. Настроить сервер и DNS; открыть 80/443 для Caddy. Выбрать место хранения и обработки данных с учётом требований компании.
4. В `.env`: `SITE_ADDRESS=example.ru`, `SITE_URL=https://example.ru`, `PUBLIC_ORIGIN=https://example.ru`, `SECURE_COOKIES=true`. Пароли — уникальные, не из примера. API и PostgreSQL не публиковать напрямую.
5. Заполнить SMTP; TLS включён по умолчанию. Проверить тестовое обращение и получение письма. Включить приём только с утверждённой политикой и её версией.
6. Включить `SITE_INDEXABLE=true` и пересобрать frontend. До этого robots запрещает индексацию; это не ограничение доступа.
7. Настроить внешнюю проверку `/api/health/ready`, резервное копирование и уведомления о недоступности. Назначить ответственного за новые заявки, ошибки почты и своевременное удаление персональных данных.

## Резервные копии

Из корня проекта: `./scripts/backup.sh`. Сохраняются дамп PostgreSQL и папка media с приватными правами файлов. Скрипт не создаёт расписание: его нужно включить в планировщик сервера. Хранить зашифрованную копию вне основного сервера; `.env` резервировать отдельно в защищённом хранилище. Определить сроки хранения заявок и резервных копий до запуска.

Проверка восстановления **в отдельную пустую БД**, не поверх рабочей:

```sh
# Создание отдельной БД для проверки
 docker compose exec -T db createdb -U mabetek mabetek_restore_check
 docker compose exec -T db pg_restore -U mabetek -d mabetek_restore_check --no-owner < backups/SELECTED.dump
 docker compose exec -T db psql -U mabetek -d mabetek_restore_check -c 'SELECT count(*) FROM leads;'
```

Медиа восстанавливать в отдельную временную папку, проверять содержимое, затем переносить при остановленном обслуживании. Удаление проверочной БД и переключение рабочей системы выполняет оператор после проверки.

## Обновление

Сначала резервная копия, затем новый код, `docker compose up --build -d`, проверка статусов и `/api/health/ready`. Новые изменения схемы оформлять миграциями. Не редактировать уже применённые миграции. Откат кода не гарантирует совместимость со старой схемой: сначала оценить конкретную миграцию.

## Безопасность

Админка — один служебный аккаунт, Argon2, подписанная HttpOnly/SameSite Strict сессия на 8 часов. Смена хеша пароля отзывает старые сессии. Изменяющие запросы админки требуют точного Origin. Не добавлять CORS `*` с cookies. При проксировании цепочкой внешних CDN отдельно настроить доверенные прокси, иначе лимит может применяться к адресу CDN.

Ограничитель частоты — атомарные счётчики в БД; IP записывается только в виде HMAC в пределах окна. HTTP-логи сервера сами по себе могут содержать адреса: срок их хранения задаётся на сервере. Персональные данные не помещать в URL и сообщения исключений.

Почтовый воркер не записывает полные ответы SMTP в БД, чтобы не сохранить секреты. Максимальный размер запроса ограничен Caddy; приложение дополнительно проверяет Content-Length. Caddy обязателен как входная точка в производстве.

HTML из пользовательских полей не исполняется: публичный интерфейс использует React-экранирование, письмо — plain text. Не заменять это на `dangerouslySetInnerHTML` без отдельного дизайна очистки HTML.
